**Status:** Authoritative Documentation Standard

**Purpose:** This document defines how Codex must work inside the MetaSiberia repository.

## Source priority

1. Working code (master)
2. Verified project architecture
3. Confirmed project and runtime data
4. This MCOS document
5. Current documentation in docs/codex
6. Legacy documentation

## Scope and interpretation

MCOS defines engineering and knowledge-organisation standards. It is not a
description of the current implementation. Statements about components,
Scientific Objects and future capabilities are normative targets unless the
working code and docs/codex explicitly mark them as implemented. Working code
has absolute priority; production status requires a dated live verification.

## Appendix A — Working with AGENTS.md
### A.1 Назначение AGENTS.md

Файл AGENTS.md является точкой входа для любой новой сессии Codex.

Он не является документацией проекта.

Он не является README.

Он не является архитектурным описанием.

Его единственная задача — объяснить Codex, как работать именно с этим проектом.

Любая информация, не влияющая на поведение Codex, должна храниться в других документах.

### A.2 AGENTS.md — это загрузчик

Представляй AGENTS.md как загрузчик операционной системы.

Он не содержит всю систему.

Он говорит:

где находятся знания;
в каком порядке их читать;
какие правила являются обязательными;
чего делать нельзя;
как начать работу.

Всё остальное должно находиться в docs/codex.

### A.3 Главный принцип

Размер AGENTS.md должен оставаться небольшим.

Рекомендуемый объём:

минимум — около 100 строк;
максимум — около 300 строк.

Если файл начинает превращаться в руководство пользователя, это означает, что информация должна быть вынесена в профильные документы.

### A.4 Обязательная структура

Каждый корневой AGENTS.md должен содержать следующие разделы:

Назначение проекта.
Главные архитектурные правила.
Порядок исследования проекта.
Ограничения.
Работа с документацией.
Правила экономии токенов.
Ссылки на docs/codex.

Не добавляй разделы без практической необходимости.

### A.5 Что нельзя помещать в AGENTS.md

Запрещается хранить:

полное описание архитектуры;
подробные команды сборки;
историю изменений;
длинные инструкции по разработке;
большие таблицы;
подробные карты каталогов;
список всех классов;
описание каждого редактора.

Эта информация должна находиться в специализированных документах.

### A.6 Локальные AGENTS.md

Локальный AGENTS.md создаётся только тогда, когда каталог действительно имеет собственные правила.

Например:

сервер;
клиент;
web client;
редакторы;
документация;
скрипты;
инфраструктура.

Не создавай локальные инструкции в каждой папке.

### A.7 Наследование правил

Правила применяются сверху вниз.

Корневой AGENTS.md
        ↓
Локальный AGENTS.md
        ↓
Документация подсистемы

Локальный файл дополняет корневой.

Он не должен его копировать.

### A.8 Разрешение конфликтов

Если два AGENTS.md содержат противоречащие правила:

определить область действия;
использовать наиболее локальный файл;
если конфликт остаётся — обновить документацию.

Конфликтующие инструкции не должны существовать долго.

### A.9 Когда обновлять AGENTS.md

Корневой AGENTS.md обновляется только если изменились:

правила работы Codex;
структура документации;
обязательный порядок исследования;
политика безопасности;
политика экономии токенов.

Появление нового редактора само по себе не является причиной изменения корневого файла.

### A.10 Когда создавать новый локальный AGENTS.md

Создавай новый локальный файл только если выполняются одновременно несколько условий:

подсистема большая;
у неё собственные правила;
эти правила регулярно используются;
они не подходят для остальных частей проекта.
### A.11 Когда удалять локальный AGENTS.md

Если локальный файл:

дублирует корневой;
больше не содержит уникальных правил;
относится к удалённой подсистеме,

его следует удалить, а уникальные сведения перенести в соответствующую документацию.

### A.12 Проверка качества AGENTS.md

Перед завершением задачи проверь:

файл не содержит дублирования;
ссылки актуальны;
правила соответствуют текущей архитектуре;
отсутствуют устаревшие команды;
отсутствуют временные инструкции;
отсутствуют сведения, относящиеся только к одной завершённой задаче.
### A.13 Стандарт поведения

Любая новая сессия Codex должна выполнять следующий алгоритм:

Открыть AGENTS.md
        ↓
Определить область задачи
        ↓
Найти ближайший локальный AGENTS.md
        ↓
Открыть необходимые документы из docs/codex
        ↓
Определить минимальный набор файлов
        ↓
Только затем читать исходный код

Этот алгоритм является обязательным для всех дальнейших задач в проекте MetaSiberia.

## Appendix B — Scientific Object Editor Development Standard

Статус приложения:

Нормативная целевая модель официальной WIP-подсистемы. Перечисленные ниже
возможности не считаются реализованными без подтверждения кодом. Текущая модель,
ограничения и placeholders фиксируются в
docs/codex/scientific-object-editor.md и docs/codex/current-state.md.

### B.1 Назначение

Scientific Object Editor рассматривается как стратегическая WIP-подсистема MetaSiberia.

Он предназначен для создания, редактирования, хранения, визуализации и анализа научных объектов непосредственно внутри метавселенной.

Редактор должен стать универсальной платформой для различных научных дисциплин, а не специализированным инструментом только для одной области.

### B.2 Стратегическая цель

Научный редактор должен позволять пользователям работать с научными данными так же естественно, как сейчас они работают с деревьями, частицами или ландшафтом.

В долгосрочной перспективе MetaSiberia должна поддерживать:

научные исследования;
образование;
моделирование;
совместную работу;
публикацию результатов;
интерактивные демонстрации;
обучение с использованием трёхмерных объектов.
### B.3 Архитектурный принцип

Редактор проектируется вокруг понятия научного объекта, а не вокруг конкретной дисциплины.

Базовый интерфейс должен быть одинаковым независимо от того, работает пользователь с молекулой, графом, кристаллом или планетой.

### B.4 Поддерживаемые дисциплины

Первое целевое направление:

химия.

Далее архитектура должна позволять добавлять без перепроектирования:

физику;
биологию;
астрономию;
геологию;
математику;
медицину;
материаловедение;
инженерию;
пользовательские научные расширения.
### B.5 Принцип расширения

Добавление новой дисциплины не должно требовать изменения уже реализованных дисциплин.

Новая дисциплина должна подключаться как расширение существующей системы.

### B.6 Базовый жизненный цикл научного объекта

Каждый научный объект проходит одинаковый цикл:

Создание
        ↓
Редактирование
        ↓
Визуализация
        ↓
Сохранение
        ↓
Загрузка
        ↓
Совместное использование
        ↓
Экспорт
### B.7 Представление объекта

Любой научный объект состоит из нескольких уровней:

логическая модель;
данные;
визуальное представление;
свойства;
пользовательский интерфейс;
сериализация.

Эти уровни должны быть максимально независимыми.

### B.8 Данные важнее визуализации

Визуализация является отображением данных.

Она не должна быть единственным источником информации.

Если завтра появится новый способ отображения объекта, логическая модель должна остаться неизменной.

### B.9 Сериализация

Каждый научный объект должен иметь единый механизм сохранения.

Нельзя использовать отдельный формат хранения для каждого нового типа объекта без веской причины.

### B.10 Визуализация

Редактор не должен зависеть от одного способа отображения.

Один и тот же объект может иметь несколько представлений:

реалистичное;
учебное;
схематическое;
каркасное;
аналитическое;
пользовательское.

Переключение представлений не должно изменять сами данные.

### B.11 Интеграция с движком

Научный объект является обычным объектом мира MetaSiberia.

Он должен использовать существующую систему:

трансформаций;
выбора;
сцены;
ресурсов;
сохранения мира;
сетевой синхронизации (если применимо).

Не создавать отдельную систему сцены только для научных объектов.

### B.12 Интеграция с другими редакторами

Scientific Object Editor не существует изолированно.

Он должен взаимодействовать с другими редакторами через общие механизмы проекта.

Например:

материалы;
освещение;
камеры;
анимация;
частицы;
UI;
свойства объектов.
### B.13 Пользовательский интерфейс

Редактор должен использовать общую философию интерфейса MetaSiberia.

Пользователь не должен переучиваться при переходе между редакторами.

Общие элементы управления должны вести себя одинаково.

### B.14 Искусственный интеллект

Архитектура должна предусматривать возможность использования ИИ.

Поддерживаются два режима:

локальное создание объектов;
генерация при помощи внешних языковых моделей.

При использовании внешних моделей предпочтительно использовать API, принадлежащий пользователю, а не проекту.

### B.15 Программный интерфейс

Любая операция, доступная через интерфейс, по возможности должна иметь программный эквивалент.

Это позволит:

автоматизировать создание объектов;
писать скрипты;
использовать научный редактор в будущем через API.
### B.16 Производительность

Редактор должен работать с большими объёмами научных данных.

При проектировании необходимо учитывать:

количество объектов;
количество связей;
объём памяти;
скорость отображения;
скорость сериализации.

Оптимизация должна выполняться на основе измерений, а не предположений.

### B.17 Расширяемость

Перед добавлением новой функции необходимо ответить:

можно ли реализовать её как расширение;
затронет ли она существующие дисциплины;
потребуется ли изменение базового интерфейса.

Если изменение затрагивает все существующие объекты, оно должно рассматриваться как архитектурное решение.

### B.18 Документация

Scientific Object Editor должен иметь собственую документацию, включающую:

архитектуру;
модель данных;
описание поддерживаемых дисциплин;
форматы импорта и экспорта;
API;
принципы визуализации;
рекомендации по расширению.
### B.19 Будущее развитие

Архитектура должна предусматривать возможность подключения:

внешних научных библиотек;
пользовательских модулей;
новых визуализаторов;
специализированных редакторов отдельных дисциплин.

При этом ядро Scientific Object Editor должно оставаться стабильным.

### B.20 Главный принцип

Scientific Object Editor создаётся не как отдельная функция клиента, а как долгосрочная научная платформа внутри MetaSiberia.

Каждое архитектурное решение должно приниматься с расчётом на многолетнее развитие проекта и возможность расширения без разрушения уже существующей системы.

## Appendix C — Client, Server, Website & Infrastructure Architecture
### C.1 Главный принцип

MetaSiberia — единая распределённая система.

Она состоит из нескольких логических компонентов.

Логическая подсистема не обязана быть отдельным executable, service или repository.

Codex всегда должен рассматривать их совместно.

### C.2 Основные подсистемы

Архитектурная документация должна различать следующие логические роли, когда
они подтверждены текущим проектом:

Native Client
Web Client
Realtime Server
HTTP/WebSocket Server
Public Website
Server Website
Admin Panel
Shared Engine
Scientific Editors
Asset Pipeline
Shared Libraries
Documentation System

Каждая подсистема имеет собственную область ответственности.

### C.3 Native Client

Native Client является основной пользовательской средой MetaSiberia.

Именно здесь располагаются:

редакторы;
инструменты;
интерфейс пользователя;
научные объекты;
работа с миром;
визуализация.

Новые функции пользовательского уровня должны, по возможности, сначала проектироваться для Native Client.

### C.4 Web Client

В текущей архитектуре Web Client использует ту же C++ codebase и target
gui_client через Emscripten/SDL, а webclient содержит browser shell. Он не
является самостоятельной gameplay-реализацией.

Для browser delivery допускаются собственные pipeline, оптимизация и
ограничения. Общие data/protocol contracts должны оставаться совместимыми с
Native Client.

### C.5 Shared Engine

Shared Engine — логическая общая техническая основа, а не подтверждённый
самостоятельный target. В текущем проекте она образована project-owned shared
sources и внешними glare-core/Winter boundaries.

В него должны входить только действительно общие механизмы:

математика;
сцена;
ресурсы;
сериализация;
общие форматы;
утилиты.

Редакторы не должны копировать код движка.

### C.6 Realtime Server

Realtime Server отвечает за:

соединения клиентов;
синхронизацию состояния;
мир;
игровые объекты;
обмен сообщениями;
сохранение серверного состояния.

Realtime-слой не должен владеть client UI. Это правило не означает отдельный
process: текущий executable server также включает server-rendered website.

### C.7 HTTP / WebSocket Server

HTTP/WebSocket Server отвечает за:

обслуживание Web Client;
статические ресурсы;
HTTP routes и data interfaces;
WebSocket transport общего realtime protocol;
административные маршруты.

В текущем проекте он встроен в executable server и использует общий state.
Логически это отдельная область ответственности, но не отдельный deployment.
Отдельный REST/OpenAPI backend не считается существующим без code evidence.

### C.8 Public Website

Основной сайт предназначен для:

представления проекта;
публикации информации;
привлечения пользователей;
документации;
презентации возможностей MetaSiberia.

Он не должен зависеть от внутреннего интерфейса администратора. Source и deploy
текущего metasiberia.com в данном repository не подтверждены; не приписывать
ему webserver assets без внешнего source evidence.

### C.9 Server Website

Server Website связан с серверной инфраструктурой.

Текущий Server Website встроен в server process и предоставляет:

Web Client;
серверные страницы;
административные интерфейсы;
служебные HTTP/data routes.

Не смешивай его документацию с Public Website.

### C.10 Admin Panel

Административная панель является самостоятельной логической подсистемой, но в
текущем проекте это server-rendered routes /admin* внутри Server Website, а не
отдельный executable, service или SPA.

Её задачи:

управление сервером;
управление данными;
мониторинг;
административные действия.

Административный интерфейс никогда не должен использоваться как публичный API.

### C.11 Общая модель данных

Все основные подсистемы должны использовать общую модель данных.

Если появляются две несовместимые модели для одного и того же объекта, это рассматривается как архитектурная проблема.

### C.12 Общие интерфейсы

Общие интерфейсы должны быть едиными.

Например:

идентификаторы объектов;
трансформации;
свойства;
материалы;
сериализация.

Не создавать альтернативные версии без необходимости.

### C.13 Asset Pipeline

Ресурсные изменения должны использовать подтверждённый существующий pipeline.
Текущий pipeline частично состоит из CMake/scripts и частично из ручных стадий;
не объявлять его полностью централизованным или воспроизводимым без проверки.

Он отвечает за:

импорт;
преобразование;
генерацию;
упаковку;
публикацию ресурсов.

Редакторы должны переиспользовать существующие resource/upload/copy mechanisms,
а не создавать параллельную систему обработки без архитектурного решения.

### C.14 Web Pipeline

Pipeline Web Client должен быть описан отдельно.

Не смешивай:

исходные ресурсы;
промежуточные данные;
сгенерированные файлы;
опубликованные ресурсы.

Каждый этап должен быть документирован.

### C.15 Серверные данные

Server State рассматривается как отдельная подсистема хранения.

Не изменяй формат хранения без анализа:

совместимости;
производительности;
восстановления;
миграции.
### C.16 Разделение ответственности

Каждая подсистема отвечает только за собственную область.

Например:

Client не должен выполнять функции Server.

Server не должен выполнять функции Editor.

Website не должен выполнять функции Admin.

Admin не должен становиться API общего назначения.

### C.17 Потоки данных

Документируй реальные направления потоков данных.

Например:

Редактор
        ↓
Научный объект
        ↓
Сериализация
        ↓
Хранилище
        ↓
Загрузка
        ↓
Визуализация

Не рисуй схемы, которые не подтверждаются кодом.

### C.18 Новые подсистемы

При появлении новой крупной подсистемы необходимо:

определить её роль;
определить владельца данных;
определить зависимости;
определить точки интеграции;
обновить карту проекта;
обновить архитектурную документацию.
### C.19 Production

Production является одной из архитектурных сред.

Он должен рассматриваться отдельно от:

локальной разработки;
тестовой среды;
staging.

Документация должна явно разделять эти среды.

### C.20 Главный принцип

Архитектура MetaSiberia должна оставаться модульной.

Добавление новых возможностей должно происходить через расширение существующих подсистем, а не через создание параллельных архитектур.

Конец Приложения C.

<a id="appendix-d"></a>

## Appendix D — Coding Standards & Engineering Rules
### D.1 Главный принцип

Код MetaSiberia должен быть понятен человеку.

Компилятор понимает практически любой корректный код.

Архитектор проекта должен понимать его через несколько лет.

Поэтому главным критерием качества является читаемость.

### D.2 Код отражает архитектуру

Структура файлов должна повторять архитектуру проекта.

Не создавать каталог только потому, что "так удобнее".

Каждый каталог отвечает за одну область ответственности.

### D.3 Один класс — одна ответственность

Каждый класс должен иметь одну основную роль.

Если описание класса начинается словами:

Этот класс также...

или

Кроме того...

это сигнал проверить необходимость разделения ответственности.

### D.4 Минимальная связность

Подсистемы должны знать друг о друге как можно меньше.

Используй:

интерфейсы;
абстракции;
сообщения;
регистрацию компонентов.

Избегай прямых зависимостей между удалёнными частями системы.

### D.5 Предпочитай существующие решения

Перед созданием нового класса проверь:

существует ли похожий класс;
существует ли общий интерфейс;
существует ли подходящий менеджер;
существует ли механизм регистрации.

Новый код — последнее средство.

### D.5.1 Принцип инженерной ответственности

Перед внесением изменения Codex должен понимать:

какую проблему решает изменение;
какие подсистемы затрагиваются;
какие зависимости появляются;
увеличивает или уменьшает изменение сложность проекта;
как оно повлияет на сопровождение через несколько лет.

Если последствия невозможно объяснить, изменение не должно выполняться автоматически.

### D.5.2 Работа с техническим долгом

Найденный долг не является разрешением на попутный ремонт.

Проблема должна быть классифицирована:

Engineering Debt;
Documentation Debt;
Build Debt;
UX Debt;
Performance Debt;
Security Debt.

Для каждой подтверждённой проблемы указываются:

описание;
причина;
последствия;
приоритет;
предлагаемый способ решения.

Исправление выполняется только в рамках текущей задачи или по отдельному решению владельца.

### D.6 Именование

Названия должны отражать назначение.

Плохо:

Manager2
Helper
DataClass
SystemX
ObjectNew

Хорошо:

ScientificObjectRegistry
VoxelChunkSerializer
TerrainBrush
ParticleEmitter
TreeGenerator

Название должно отвечать на вопрос:

Что делает этот объект?

### D.7 Размер функций

Функция должна выполнять одно действие.

Если функцию сложно объяснить одним предложением —

её стоит разделить.

### D.8 Размер файлов

Очень большие файлы усложняют сопровождение.

Перед увеличением файла проверь:

можно ли вынести часть логики;

можно ли создать отдельный модуль;

можно ли использовать существующий механизм.

Не дроби код искусственно.

### D.9 Комментарии

Комментарии должны объяснять почему, а не что.

Плохо:

// Увеличиваем i
i++;

Хорошо:

// Индекс начинается с единицы, так как нулевой элемент зарезервирован системой.
### D.10 Документирование архитектуры

Если участок кода сложно понять без знания архитектуры —

архитектурное объяснение должно находиться в документации, а не в длинном комментарии внутри кода.

### D.11 Ошибки

Не скрывай ошибки.

Если система может определить причину —

она должна сообщить её.

Избегай конструкций:

catch(...)
{
}

если исключение можно обработать корректно.

### D.12 Логирование

Логи предназначены для диагностики.

Не использовать логирование как замену обработке ошибок.

Каждая запись должна отвечать на вопрос:

Что произошло?

Почему произошло?

Что делать дальше?

### D.13 API

Любой публичный интерфейс должен быть максимально стабильным.

Изменение API требует:

анализа последствий;
обновления документации;
проверки всех потребителей.
### D.14 Сериализация

Формат хранения данных должен быть независим от пользовательского интерфейса.

UI не должен влиять на структуру сохраняемых данных.

### D.15 Работа с памятью

Предпочитай объекты с понятным временем жизни.

Избегай неочевидного владения памятью.

Любой ресурс должен иметь очевидного владельца.

### D.16 Производительность

Не оптимизируй без измерений.

Если предполагается, что участок кода является узким местом:

подтвердить это измерениями;
выбрать минимальное изменение;
документировать архитектурные последствия.
### D.17 Редакторы

Все редакторы должны придерживаться одинаковых инженерных правил.

Новый редактор должен ощущаться частью MetaSiberia, а не отдельной программой.

### D.18 Общие компоненты

Если два редактора используют одинаковую логику —

она должна быть вынесена в общий модуль.

Не копируй код между редакторами.

### D.19 Конфигурации

Конфигурационные данные должны храниться отдельно от исходного кода.

Не размещай значения, зависящие от окружения, непосредственно в коде.

### D.20 Главный принцип

Инженерные стандарты существуют не для ограничения разработчика, а для того, чтобы проект оставался понятным, предсказуемым и расширяемым на протяжении многих лет.

Конец Приложения D.

бага;

добавить в project-index.md;

Интегрировать в существующий редактор

что именно улучшится;

Проверить:

изменилась ли архитектура;
появился ли новый компонент;
изменились ли пути;
изменились ли правила разработки.

Только чтение

### E.11 Workflow — Работа с сайтами

Public Website;
Server Website;

касается ли изменение Realtime Server;

Определить все подсистемы
        ↓

        ↓
Выполнить изменения по этапам
        ↓
Обновить документацию один раз в конце

Если изменение локальное:

не исследовать весь репозиторий;
не выполнять повторный аудит;
не перечитывать архитектуру;
работать только с нужной подсистемой.
### E.15 Workflow — Самопроверка

✔ изменены только нужные файлы;

✔ архитектура не нарушена;

✔ новые знания сохранены.

        ↓

        ↓

        ↓

Если одна и та же последовательность действий используется регулярно, она должна быть оформлена как стандартный Workflow и использоваться всеми будущими сессиями Codex.

## Appendix F — Documentation & Knowledge Maintenance
### F.1 Назначение

Документация MetaSiberia является постоянно развивающейся системой знаний.

Её задача — уменьшать стоимость разработки, сопровождения и исследования проекта.

Документация должна быть полезной как человеку, так и будущим сессиям Codex.

### F.2 Главный принцип

Документация должна отвечать на реальные вопросы разработчика.

Не писать документы ради количества.

Если документ не помогает выполнять работу быстрее или безопаснее, его существование должно быть пересмотрено.

### F.3 Жизненный цикл документа

Каждый документ проходит одинаковые стадии.

Создание
        ↓
Использование
        ↓
Дополнение
        ↓
Проверка
        ↓
Обновление
        ↓
Архивация

Удаление документа допускается только после анализа его роли.

### F.4 Постоянная проверка актуальности

Во время работы регулярно проверяй:

соответствует ли документ текущему коду;
существуют ли все упомянутые файлы;
существуют ли все пути;
существуют ли все ссылки;
существуют ли описанные команды.

Если нет — документ необходимо обновить.

### F.5 Обновление после архитектурных изменений

Если изменились:

структура проекта;
архитектура;
формат данных;
точки входа;
редакторы;
pipeline;
API;

необходимо сразу обновить соответствующую документацию.

Не откладывать обновление.

### F.6 Что считается новым знанием

Новым знанием считается только устойчивая информация.

Например:

новый редактор;
новый формат;
новая архитектурная зависимость;
новый серверный компонент;
новый жизненный цикл объекта.

Не сохраняй:

временные идеи;
личные заметки;
промежуточные эксперименты;
гипотезы.
### F.7 Архивация

Если документ больше не используется:

проверить наличие ссылок;
определить замену;
переместить в архив;
указать причину.

Архив не должен мешать основной документации.

### F.8 Проверка ссылок

Каждый документ должен содержать только рабочие ссылки.

Проверять:

относительные пути;
ссылки на другие документы;
ссылки на каталоги;
ссылки на изображения;
ссылки на диаграммы.
### F.9 Карта знаний

В проекте должна существовать единая карта знаний.

Она должна позволять определить:

где искать архитектуру;
где искать правила разработки;
где искать карту проекта;
где искать описание данных;
где искать инструкции Codex.
### F.10 Минимизация документации

Если два документа можно объединить без потери качества —

их следует объединить.

Если один документ становится слишком большим —

его следует разделить по смысловым областям.

### F.11 Документирование решений

Каждое важное архитектурное решение должно отвечать на вопросы:

Что изменено?
Почему?
Какие последствия?
Что необходимо учитывать в будущем?
### F.12 Работа с диаграммами

Диаграммы должны отражать архитектуру.

Не использовать диаграммы только ради визуального оформления.

При изменении архитектуры диаграммы обновляются одновременно с текстом.

### F.13 Работа с примерами

Примеры должны быть минимальными.

Они должны демонстрировать идею, а не повторять реальный код проекта.

### F.14 Качество документации

Хорошая документация:

легко читается;
легко обновляется;
не противоречит коду;
помогает искать информацию;
не содержит лишних деталей.
### F.15 Автоматическое улучшение

После завершения задачи необходимо определить:

Можно ли сделать существующую документацию понятнее?

Если да —

улучшить её сейчас.

Не откладывать до следующего аудита.

### F.15.1 Правило создания новых документов

Новый документ допускается только если он:

документирует существующую архитектуру;
документирует подтверждённое владельцем направление развития;
закрывает реальный пробел в базе знаний;
существенно уменьшает стоимость сопровождения;
существенно уменьшает расход токенов;
улучшает навигацию.

Перед созданием необходимо проверить, нельзя ли расширить существующий canonical document.

Если польза меньше стоимости сопровождения, новый документ не создаётся.

### F.15.2 Уровни инженерной документации

Документация разделяется по ролям:

A. Конституция проекта;
B. Архитектура;
C. Навигация;
D. Правила разработки;
E. Специализированная документация;
F. История, ADR, verification и debt.

Документы разных уровней не должны смешивать задачи. История объясняет, что и почему происходило; current documentation объясняет, как система устроена сейчас.

### F.15.3 Verification Report

Verification report является итогом крупной engineering/documentation task.

Каждый крупный раздел должен фиксировать:

выполнено;
не выполнено;
почему;
оставшиеся риски;
что рекомендуется владельцу.

Не превращать verification report в журнал каждой мелкой правки.

### F.16 Главный принцип

Документация должна постоянно становиться:

короче;
точнее;
полезнее;
проще для поиска.

Никогда не допускать бесконтрольного роста количества документов.

## Appendix G — Large Repository Strategy
### G.1 Назначение

MetaSiberia является большим долгоживущим репозиторием.

Главная задача Codex — работать с ним так, чтобы масштаб проекта практически не влиял на стоимость каждой новой задачи.

### G.2 Не думай каталогами

Думай подсистемами.

Каталог — это способ хранения файлов.

Подсистема — это часть архитектуры.

Именно подсистема должна быть основной единицей анализа.

### G.3 Локализация

Перед любой задачей определить:

какая подсистема;
какие зависимости;
какие документы;
какие файлы.

На этом остановиться.

Не исследовать остальной проект.

### G.4 Новые каталоги

Если появился новый каталог:

не считать автоматически, что это новая подсистема.

Сначала определить:

архитектурную роль;
область ответственности;
связи.
### G.5 Повторное исследование

Повторный полный обход репозитория допускается только после:

крупной реорганизации;
изменения архитектуры;
отдельного указания владельца.
### G.6 Главный принцип

Размер репозитория не должен влиять на ежедневную стоимость разработки.

Это достигается:

картой проекта;
AGENTS;
системой документации;
накоплением знаний.

Конец Приложения G.

<a id="appendix-i"></a>

## Appendix I — Continuous Improvement
### I.1 Назначение

MetaSiberia развивается постоянно.

Следовательно, должна постоянно развиваться и система инструкций Codex.

MCOS не является статичным документом.

### I.2 Когда обновлять MCOS

Обновление MCOS требуется только если изменились:

архитектурные принципы;
правила работы Codex;
организация проекта;
стратегия документации;
стратегия экономии токенов.

Изменения локального кода сами по себе не являются причиной изменения MCOS.

### I.3 Что не должно попадать в MCOS

Не включать:

временные инструкции;
особенности одной задачи;
локальные обходные решения;
сведения о конкретной ошибке;
список файлов проекта;
журналы изменений.

MCOS содержит только долговременные правила.

### I.4 Проверка качества MCOS

После каждого изменения убедиться, что документ:

не содержит повторов;
не противоречит текущей архитектуре;
не дублирует рабочую документацию;
остаётся понятным новому инженеру.
### I.5 Эволюция проекта

При развитии MetaSiberia новые подсистемы должны:

интегрироваться в существующую архитектуру;
получать собственную документацию;
использовать общие инженерные принципы;
не нарушать единый стиль проекта.
### I.6 Финальный принцип

Цель MCOS — не заменить мышление инженера, а обеспечить единые правила принятия решений.

Хорошая система инструкций делает каждую следующую задачу быстрее, безопаснее и дешевле с точки зрения сопровождения.

<a id="epilogue"></a>

## Epilogue

MetaSiberia рассматривается как долгосрочная инженерная система.

Codex является её постоянным техническим помощником.

Главная задача Codex — не просто генерировать код, а сохранять архитектурную целостность проекта, поддерживать актуальную документацию, минимизировать стоимость будущей разработки и обеспечивать накопление знаний внутри самого проекта.

Каждое изменение должно делать MetaSiberia:

понятнее;
стабильнее;
расширяемее;
проще для сопровождения;
удобнее для новых разработчиков и будущих сессий Codex.

На этом базовая версия MCOS завершена.
