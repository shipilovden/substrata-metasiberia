# План: единая игровая, образовательная и экономическая система

Статус: архитектурный план, реализацию начинать только после отдельного утверждения.

## Цель

Создать общую модульную систему профиля, предметов, инвентаря, ресурсов, добычи, квестов, образования, достижений, рейтинга, магазина и внутренней экономики. Она должна работать во всех мирах, если мир или участок явно не отключил соответствующую механику.

## Архитектурные принципы

- Сервер авторитетен для предметов, ресурсов, валюты, опыта, рейтинга, квестов и наград.
- `ItemDefinition` отделён от `ItemInstance`; предметы не хранятся только строками.
- Глобальные данные аккаунта отделены от данных конкретного мира и участка.
- Баланс хранится через Ledger, а не одним изменяемым числом.
- Все действия имеют idempotency key и журнал событий, чтобы повторная доставка не выдавала награды повторно.
- Механики data-driven: definitions JSON/ресурсные файлы с version, namespace, локализацией, лицензией и миграцией.
- Не создавать единый `GameManager`; каждый модуль имеет собственный owner и интерфейс.

## Модули

```text
Account/Profile
  -> Inventory/Items/Equipment
  -> Resources/Harvesting/Crafting
  -> Quests/Education/Achievements/Rating
  -> Economy/Shop/Ledger
  -> Notifications/EventBus/Statistics
```

Основные классы: `Account`, `Profile`, `Inventory`, `InventorySlot`, `InventoryContainer`, `ItemDefinition`, `ItemInstance`, `ItemStack`, `ItemTransaction`, `EquipmentSlot`, `ResourceDefinition`, `ResourceNodeComponent`, `HarvestAction`, `ToolDefinition`, `DropTable`, `Wallet`, `CurrencyDefinition`, `LedgerTransaction`, `QuestDefinition`, `QuestInstance`, `QuestObjective`, `EducationModule`, `AchievementDefinition`, `RatingRule`, `Leaderboard`, `WorldMechanicConfig`.

## Scope данных

| Scope | Примеры |
|---|---|
| Глобальный аккаунт | UID/UUID, профиль, достижения, сертификаты, глобальная валюта |
| Персонаж | экипировка, личный инвентарь, опыт, настройки |
| Мир | включённые механики, локальные магазины, квесты, рейтинги, ресурсные узлы |
| Участок | права добычи, локальные запреты, владельцы, правила повреждения |
| Клиент | UI-состояние, thumbnails, временный кэш; не authoritative state |

## Поток добычи

```text
raycast клиента -> доступное действие -> запрос HarvestAction
  -> сервер: расстояние/права/инструмент/cooldown/состояние узла
  -> атомарное уменьшение ресурса + durability инструмента + drop/XP
  -> событие EventBus -> частицы/звук/анимация клиента
  -> журнал и синхронизация WorldObject/Inventory
```

Обычная модель дерева или камня не является ресурсом автоматически. Для этого нужен `ResourceNodeComponent` со state `full`, `damaged`, `nearly_depleted`, `depleted`, `regenerating`, `disabled`, capacity, regeneration, requiredTool, dropTable, duration, distance, parcel/world rules и visualStages.

## Анимация удара и эффект щепок

Отдельная анимация нужна только если в текущем avatar animation set нет подходящего клипа. В найденных ресурсах проекта готовых `axe/chop/harvest` ассетов не обнаружено, поэтому для качественного MVP следует добавить или создать отдельный клип: замах, удар, возврат инструмента и, при необходимости, варианты одной/двумя руками.

Анимация не должна сама начислять ресурс. Поток должен быть таким:

```text
HarvestAction accepted by server
  -> client starts axe animation
  -> animation hit-window / notify
  -> server validates impact and commits resource change
  -> replicated result -> wood chips + sound + damage stage
```

Щепки — это отдельный визуальный эффект, а не часть основного mesh дерева: particle emitter с коротким burst, направлением от точки удара, случайным разбросом, небольшими фрагментами коры и звуком удара. Сервер синхронизирует факт успешного удара и seed/параметры эффекта; клиент создаёт частицы локально. При отключённых эффектах мира должна оставаться логика добычи без визуального burst.

Нужны также: cancel при потере инструмента/дистанции, cooldown, защита от повторного hit-event, fallback на базовую gesture-анимацию, отсутствие влияния на render loop и тесты повторной доставки сетевого события. Покупать готовые анимации заранее не требуется: сначала нужно проверить существующий avatar rig и лицензии; затем выбрать licensed asset или заказать один production-клип.

## Профиль и UI

В существующем стиле клиента добавить панели: Профиль, Инвентарь, Снаряжение, Ресурсы, Магазин, Квесты, Образование, Достижения, Рейтинг, Статистика, История, Настройки. Экипировка остаётся быстрым wearable-интерфейсом, полный инвентарь — отдельным хранилищем.

Кнопки и индикаторы используют существующие SVG-иконки и toolbar/dock lifecycle. Мир может отключать отдельные вкладки и действия через `WorldMechanicConfig`.

## Экономика и магазин

`Wallet` является проекцией Ledger. Операции: purchase, sale, reward, refund, transfer; статусы `pending/completed/failed/reversed/cancelled/disputed`. Реальные платежи не входят в MVP. Сначала — тестовые баллы или внутренняя валюта.

## Образование, квесты, рейтинг

Квесты и уроки описываются данными, а не отдельным C++ кодом. `QuestObjective` может ссылаться на объект мира, измерение, CAD-объект, ресурс или событие. Рейтинг разделяется по категориям и сезонам, учитывает сложность, подтверждение и командную работу; простой гринд ресурсов не должен быть рейтингом.

## Сетевой контракт и безопасность

На первом этапе использовать существующие сообщения только для небольших descriptors; authoritative account/inventory/economy state требует новых versioned server handlers и миграции. Клиент не может сам начислять предметы, валюту, XP или рейтинг. Все команды проверяют permissions, nonce/idempotency, scope мира и повторяемость.

## Этапы

0. Аудит текущих account/world/protocol/storage boundaries.
1. Профиль и базовая статистика.
2. Item Registry, ItemInstance, Inventory и синхронизация.
3. Resource Registry, ResourceNodeComponent, топор/кирка, дерево/камень, дроп и восстановление.
4. EventBus, QuestDefinition/Instance и награды.
5. Образовательные модули, тесты, роли и отчёты.
6. Достижения, категории рейтинга, сезоны и антинакрутка.
7. Ledger, внутренняя валюта и каталог магазина.

Для каждого этапа обязательны server/client tests, permission tests, reconnect/conflict tests, migration plan, criteria of readiness и rollback strategy.

## Минимальный MVP

Профиль → один ItemDefinition → серверный инвентарь → топор как ItemInstance → один ResourceNode дерева → серверная добыча → древесина в инвентарь → XP и журнал события. Это доказывает основной игровой цикл без магазина и реальных платежей.
